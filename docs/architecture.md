# 设计：少几个进程，边界更清楚

这个项目不是把旧脚本逐行翻译成 Go。保留的是状态发布的规则；账号网关、订阅数据库、系统代理控制器和个人机器路径没有一起搬过来。

```text
Codex ── HTTP/SSE ── 本地唯一服务 ── 与快照绑定的出口 ── 上游
                         │
                         ├─ 按凭据、账号、模型隔离的 active / ready
                         ├─ 串行、限频的短探测
                         ├─ 订阅解析与内嵌出站适配
                         └─ 元数据日志、配置事务、同端口 Web 管理面板
```

## 一份 state 的生命周期

`turnstate.Parse` 只读封装：版本字节、签发时间和密文块数。个人规则是 10 块 / 通常 292 字符，Team 规则是 12 块 / 通常 332 字符；估计 TTL 为 3600 秒，最后 30 秒不再接纳新请求。这些是经验参数，不是上游规格或质量指标。

账号规则可手动指定，自动模式只把请求令牌里的套餐字段当作未验证提示，并检查提示账号与当前工作区是否一致。未知时说明采用的规则，不从长度反推身份。旧配置的非默认 `baseline_blocks` 在自动模式中保留；明确个人/Team选择覆盖它。每个请求仍由上游完成真实认证。

采集结果通过 `Store.Offer` 进入状态机：

- 没有可用 active，合格候选直接发布。
- active 还健康，新候选留在 ready，不抢正在工作的主值。
- active 接近续补窗口，签发时间更新的 ready 可以晋升。
- 同一 active 版本连续两次收到非基线响应，另一指纹的可用 ready 可以接替。
- 旧版本请求的晚到响应不能给新版本累计 strikes。

每次转发只拿一份值类型快照，内容包括 token、出口索引和版本。后续晋升不会改变这个请求已经拿到的值。生产请求不再依赖多个进程各自读写同名文件。

候选观测只有计数；没有无界增长的候选日志。合格 active 和有限数量的 standby 会写入数据目录的 0600 私有备份，按认证/账号/模型/上游哈希隔离，不保存认证头；重启后只恢复仍未过期且原出口仍存在的候选。

## 为什么回包不能直接更新 active

响应头是观测，不是发布命令。如果回包一到就覆盖主值，正在运行的请求与下一条请求可能拿到不同来源甚至不同形状的状态，排查会很困难。

因此响应中的 state 只能影响观测计数和当前版本的 strikes；采集调度是唯一发布入口。认证和限流状态码另行进入共享暂停逻辑，不因 active 仍有效而继续请求。缺失响应头时保留现状，不把“没有信息”硬说成失败。

## 为什么不自动重放生成请求

代理收到不合格形状时，上游可能已经开始推理。即使没有把正文交给客户端，再发一遍也可能重复消耗额度，甚至让工具调用语义变复杂。

对于正式生成响应的形状异常，在发送响应正文前返回明确的 503，让使用者决定下一步。服务不重放；生成的 Codex provider 配置也把普通请求和流恢复重试设为 0。用户或不同客户端仍可能主动重试，所以不能承诺全链路“恰好执行一次”。

## 没有 state 的可用性选择

转发内核在 `state_fallback` 为空时仍按 `strict` 处理。`setup` 已收敛为启动即自动接入：从未明确选择策略时设为 `passthrough`，已经明确设为 `strict` 则保留。首页接入按钮用于再次修复，确认后会选择 `passthrough`；连接设置也可手动选择。明确选择 `passthrough` 后，只有正式生成尚未发送、采集后仍无可用值且没有账号拒绝时，才转发一次不注入的原请求，响应头标注 `fallback-passthrough`。这不是重试、不是改写形状、不是暂停解除；上游响应之后不能靠它重放请求。

关闭注入和兜底是两个不同开关。兜底模式仍允许预算内采集；关闭注入则停止采集和替换。官方普通转发保留客户端原本携带的 state，只有本服务实际注入时才覆盖为已采集值；中转仍清除官方 state。上游 401/403/429 状态在同账号的模型会话间共享，不会因为从 Astra 切到 Sol 就重新获得一次尝试。

## 为什么只开 HTTP/SSE

WebSocket 要在升级后的消息帧中继续检查模型、会话和状态边界。仅转发握手却不处理后续帧，很容易把模型、账号和 state 的隔离变成口头约束。

首条请求在采到一份合格 state 后立即转发，不等备用采集。备用不足时，后台按冷却间隔补充；后台与前台都复用同一个串行采集入口。

当前仍将 `supports_websockets` 设为 `false`，遇到升级请求明确返回 426。SSE 保持即时 flush，客户端取消会传播给上游，单个请求最长 30 分钟。没有用缺一半校验的 WebSocket 实现冒充兼容。

支持的路径是 Responses 生成、Responses compact、模型列表，以及 Codex 的独立搜索路径。模型列表和搜索不注入模型 state。不是任意路径的开放反向代理。

### 请求体压缩也要兼容

官方 OAuth 客户端可能发送 zstd，API key 测试路径不一定暴露这一点。网关支持未压缩 JSON、gzip 和 zstd，压缩输入与解压后正文分别限制 16 MiB，zstd 内存/窗口也有限制；损坏、截断、未知、多层编码或超限请求不会发到上游。解码后仍走模型与操作校验，转发时不保留失效的 Content-Encoding 声明。

### 远程压缩不是普通生成

V1 是原样转发的 `/responses/compact`；V2 是 `/responses` 中携带 `compaction_trigger` 的压缩请求。网关先识别操作类型，再决定是否进入采集；压缩不等待 state、不发额外采集、不因响应 state 形状而返回普通生成的拦截错误，也不把 V1 改写成 V2。

r16 起，注入开启且已有合格主 state 时，官方压缩请求携带该主票并保持来源出口；不触发采集，也不使用压缩响应的 state 更新或撤销聊天主备票。没有可用票或注入关闭时保留客户端头；中转继续清除官方头。没有可用 state 也可以按配置出口转发压缩。认证拒绝与限流仍共享，压缩不会因此绕过暂停。

配置层保留官方 `OpenAI` provider 名称，因为核对的 Codex 0.154.0 会用该名称判断远程压缩能力。中转保留原 provider 名称，不凭本地声明把不支持压缩的上游变成支持。V1、V2 和压缩后的下一轮都要独立验收，见[问题清单](issues-and-verification.md#p01-远程上下文压缩优先项)。

## 代理核心为什么内嵌

HTTP/SOCKS5 自己实现不难，但各类加密节点的握手、TLS 和传输细节不适合在这里再造一遍。项目复用 Mihomo 的出站适配器与 URI 转换器，不启动它的控制面、DNS 服务、TUN 或本地监听。

代价是依赖和二进制体积明显大于一个纯 HTTP 代理。换来的是单文件分发、单进程运行，以及成熟协议实现。外层对导入格式、节点数量、危险字段和日志做限制。订阅节点失败不会自动走直连。

面板应用来源或固定路由时，控制层等待前台请求结束，暂停旧引擎的后台采集，检查是否有认证或限流暂停，然后才保存配置、关闭旧引擎并建立新一代出口。旧 state 不迁移，避免出口索引与新列表串用。失败则保留原配置和旧引擎；外部编辑 JSON 仍要求重启。

后台暂停完成后才检查拒绝状态，是为了防止“刚检查完没有限流，旧探测随后收到 429，新引擎却已经清空状态”的竞态。路由测试不带模型凭据，也不能作为解除暂停的依据。

## 配置事务

`codexconfig` 先解析当前 provider 和显式选定的 profile，区分官方 ChatGPT 与 API 通道，再生成临时本地 provider。它保留原来的上游和认证方式，不把所有配置都改成官方登录；`env_key` 仍引用原变量，API key 不返回到面板。

TOML 修改使用语法范围定位，尽量保留注释、其他 provider、项目设置和未选中的 profile。安装依次经过：原文件备份 → 事务记录和安装快照 → 检查并发变化 → 原子替换。

运行时不再只比较整个文件哈希，而是检查程序接管的模型、provider、本地入口、认证字段，以及原始上游定义和 profile 继承关系。只改注释或不相关项目设置不会让全部流量报 409；改变真正的连接或认证仍停止转发。

恢复使用原文件、安装后快照和当前文件进行三方比较。自动恢复只撤销仍能确认属于程序的修改，保留用户无关改动；不能安全定位的内联/点式 TOML 不强行改写。面板修复需要预览后的配置与事务版本仍匹配，并先归档当前文件及事务。明确选择保留当前配置时保留 CCS 新选择；明确恢复备份则会撤销之后的改动，因此必须确认。

旧版事务缺少新快照时，仅在校验能重建一致证据后处理，不能猜测或直接删事务。恢复备份和快照的校验失败均保留现场。

服务转发前检查接管配置是否仍匹配。选中的配置发生变化时停止转发，避免把新凭据送到旧上游。文件系统仍有读取与使用间的竞争窗口，因此不承诺支持多个配置管理器同时修改同一文件；切 CCS 前应先停止服务。

## 官方与 API 通道为什么分开

只有官方 ChatGPT 通道运行 turn-state 状态机。API / 中转通道沿用原 base URL，将固定本地路径 `/backend-api/codex/responses` 映射到上游的 `/responses` 路径，例如 `/v1/responses`。两边都保留 Astra、Sol、Terra 的明确模型列表及 HTTP/SSE 转发边界。

relay 模式不运行 state 探测，即使请求开启注入也不会启用。转发时移除 ChatGPT 专用身份头、turn-state、Cookie 和代理认证头；可识别的官方 OAuth token 在本地拒绝误发。认证分类仍以选中配置为依据，不能仅凭一段 opaque token 猜出它属于谁。

聊天和压缩返回的 401 / 403 / 429 由统一逻辑暂停，无论注入是否开启。其他功能单独返回的权限或额度错误原样返回，不用于判断聊天账号失效。

本地 `/backend-api/codex/` 命名空间下的 HTTP 接口统一映射到已配置上游 base URL；包括 `images/generations`、`images/edits`、`alpha/search`、模型列表以及后续新增接口。仅普通聊天执行 state 采集、注入和响应形状检查；其他请求不等待采集、不改变主备 state，multipart、二进制和压缩请求体保持原样。图片生成/编辑保留同一节点拨号器，单独允许最多 10 分钟等待响应头，避免影响聊天连接。未知功能能否使用仍取决于上游支持与权限；不会伪造成功或重复提交。管理路径、越界路径与 CONNECT/TRACE 不进入上游转发，现有 HTTP/SSE 模式不接管 WebSocket。

## 管理面板的边界

### 随机节点轮询

自动采集使用持久化的随机节点名单，每个账号/模型有独立轮次。每次实际派发前记录稳定节点 ID；同轮不重复，采集成功、批次结束、等待预算或服务重启均继续剩余名单。节点全部完成后才重新随机排序。每批探测上限、批间等待和每小时预算仍独立执行，不因为节点数量增加而加速发请求。固定/手动指定节点不消耗或重置随机名单；未访问的临时暂停节点保留为待处理，恢复前不让已处理节点开始下一轮；非固定节点连接失败及手动停用节点排除，固定节点失败后仍锁定同一入口，新增节点加入未完成轮次。

静态页面嵌入二进制，不用 CDN、不启动第二个服务。浏览器只能调用管理子路径；原模型转发接口仍拒绝浏览器 Origin / Fetch 请求。

管理端校验固定 Host、同源 Origin / Fetch 以及独立随机 Bearer 口令。口令存于本机运行记录和浏览器标签页会话存储，不通过 URL 或 cookie 传递。`setup` 自动打开页面时携带的是另一个 60 秒、一次性的 launch ticket；放在 fragment，页面读取后立即清除，再向同源管理 API 兑换会话口令。Host/Origin 仍校验，超时或重复兑换拒绝；手动登录保留。返回状态不含上游密钥、订阅 URL 或节点配置。

管理动作串行执行；请求繁忙时直接提示稍后再试，不排队积压一串操作。保存前比对磁盘配置，发现外部编辑就拒绝覆盖，并保留独立备份。

provider 字段参考 [Codex 配置 schema](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json)。客户端会更新，项目级配置和任务级覆盖也可能影响路由；没有用“能解析 TOML”代替所有桌面版本的实测结论。

## 一键入口与修复面板

CLI `setup` 只创建缺失的服务配置，已有文件不覆盖，然后进入原服务生命周期并尝试打开浏览器。启动脚本只负责找同目录二进制和传参，不注册系统服务，不下载不明文件。`doctor` 是只读状态白名单，不将上游错误自由文本转成可公开报告。

现存可读普通服务 JSON 无法加载时，`setup`/`serve` 进入独立救援模式：默认回环监听，不加载坏来源，不接管 Codex，注入关闭。重建需要用户确认及匹配的预览哈希，先归档，再生成默认配置；随后重新启动。这不掩盖端口占用、文件权限等系统层问题。

坏 Codex TOML 的重建是另一条显式流程。不能自动从残缺文件中抽取一套“看起来像”的上游和凭据。用户先明确官方/API方式，原文件备份后才生成最小替代配置；旧接管事务必须先处理，登录文件始终不改。

## 诊断不依赖模型会话

控制层记录有限条请求类别、HTTP 状态和耗时，不记录 URL、正文、凭据、订阅或 state。请求计数独立于网关会话，出口重载也不清空它。会话为空时，面板能分清从未到达与曾到达但未建立/已过期会话，避免把错误提示做成新的误导。

`setup` 自动执行接入管理事务：沿用当前模型与注入开关、保留可验证的 CCS 新配置、仅在用户没有设置兜底策略时采用普通转发。首页一键按钮是明确确认后的再次修复入口，会选择普通转发兜底。仅在尚未配置代理/订阅/固定路由时，对三个字面回环地址的常见端口执行无认证 SOCKS5 握手；不连接模型、不探外部网段、不读取代理软件配置。已有来源不被自动探测覆盖。接入结束需要重启 Codex / 新建会话，不声明旧会话被无缝热迁移。

## HTTP 成功不代表模型响应成功

采集必须看到有效 SSE 完成事件，不能只凭 HTTP 200 发布 state。明确的 `response.failed` / `error` 优先于后来出现的完成标记；通过有限白名单 code 区分模型容量与额度错误，不从自由文本猜测。`server_is_overloaded` / `slow_down` 归为容量不足，不能当作 HTTP 429；`rate_limit_exceeded` / `insufficient_quota` 进入共享暂停。容量不足和普通流失败继续本轮下一节点；明确认证和额度拒绝才提前结束，仍保留总预算与轮间间隔。未知 code 或 message 不写管理状态和常规日志。

后台采集在队列与执行期间保持会话生命周期，避免空闲清理把仍在采集的会话删掉，使它产生的拒绝状态与当前请求脱离。这个固定只覆盖实际工作，不意味着无限缓存凭据。


### r12 无主用采集

轮次节奏将主用采集与备用补充分开：`seekingActive` 以当前可用状态判断（含备用自动提升），无主用时忽略 `round_cooldown` 与旧 `nextProbe` 缓存，但每次派发仍通过持久化小时预算、存储错误检查及上游暂停。已派发记录和随机已访问名单不清零。采到首张后结束本批，有主用时恢复配置的批间等待。自然到期、撤下最后一张及重启恢复均采用同一规则。

`probeSchedule` 统一自动调度、手动请求、严格模式 Retry-After 与页面倒计时。此例外仅适用于轮次节奏，逐次退避不变；空闲和节点可用性仍在派发前检查。没有实际完成探测的批次不立即唤醒自己，避免全节点暂停时忙循环。


### r13 网络证据与手动采集（取代 r12 无主用免等待策略）

网络失败和普通 5xx 不证明 state 无效，不执行 Invalidate 或 DropRoute。非固定节点的网络失败会停止其自动采集，但已有卡与来源绑定保持；固定节点不会因网络失败进入失败清单或改用其它本地节点，后续继续尝试同一入口。手动 disabled 或其它失败原因仍拦截，真实过期及不合格响应头仍按原规则撤卡。

`collection.automatic_disabled` 缺省为 `false`，保证旧配置升级后仍保持自动采集。关闭时调度器不排队、请求引导不发探测、普通回退响应不执行 Bootstrap；已有 Store、固定节点、CollectionBudget 和上游暂停均不清空。手动入口调用独立路径，不受这个开关阻断。

自动采集在有无主用时均遵守配置批间等待（默认 180 秒）。手动 random_once 只选一个不同于主卡及上次采集的可用未暂停节点，保留配置 pin 和自动随机轮次；单次可跳过本地冷却/退避，不清空额度、不绕过上游限流。当前正在采集时不并发插入额外采集。

首次收牌观察实际完成事件，支持 gzip/zstd 解压后转发并校验；JSON Response 必须 object=response、status=completed、error 为空，缓冲最多 1 MiB。长度符合但响应无法验证时不入库，页面单独说明原因。
